# daangn_ext — 딜리버리 (클라 요구기능 통합 패키지)

기존 manual/auto 수집기(웹 SSR)를 **건드리지 않고** 얹는 드롭인 확장.
클라가 나열한 신규기능 전부를 클라 코드 스타일(daangn/ 패키지, 타입힌트, curl_cffi/aiohttp)로 구현.

### 진짜 "막힘"의 정체 규명 (핵심)

실측: 당근은 **새 세션/IP의 초기 요청 몇 건을 빈 페이지(0건)** 로 응답하고 이후 정상(수백건).
```
try0~2: len=158K  articles=0     ← 빈 껍데기(소프트블록)
try3~5: len=803K  articles=267   ← 정상
```
기존 코드는 **빈 결과를 '성공(0건)'으로 처리해 재시도 안 함** → 매물 누락 = 사용자가 겪은 "당근이 막는다".
**수정**(`daangn_ext/robust.py`): 빈 결과=소프트블록 → 세션쿠키 유지 + 재시도. patched/manual_api.py 반영.
검증: 청담동 루이비통 275건(재시도 2회), 역삼동 샤넬 275건(재시도 12회) 극복.

## ★ 전국 검색 시간 + N계정 선형단축 (실측·2026-08-26)

- **전국 검색단위 = 동(depth3) 6,537개** (OUT.json 기준)
- 지역당 정상 응답 = **0.45초(median)** — 대부분 즉시
- 단, 단일 IP는 간헐 스로틀로 일부 지역 빈응답(재시도 필요, 심하면 데이터 손실)

**IP당 스로틀 실증**: 같은 IP로 8개 지역 **동시요청 → 8/8 전부 빈응답(0건)**.
→ **한 IP 안에서는 병렬 불가**(버스트=전멸). 한 IP는 순차+페이싱만 가능.
→ **병렬은 서로 다른 IP(프록시)로만.** 프록시가 속도+완전성 양쪽에 필수.

### N계정 선형단축 = YES (조건부)

병목이 **IP당**이므로, 계정(=프록시IP) N개 = 독립 레인 N개 = **~N배 단축**:

| 레인(프록시IP) | 전국 1브랜드 소요(추정, 0.45s/지역) |
|---|---|
| 1 | ~49분 |
| 10 | **~5분** |
| 20 | ~2.5분 |

**"1계정 10분 → 10계정 1분"** → 방향 맞음(거의 선형). 단 필수조건:
1. **10계정이 각각 다른 프록시 IP** 여야 함. 10계정이 같은 IP면 = 0배(전부 스로틀).
2. 각 레인은 **순차+페이싱**(한 IP 버스트 금지). 병렬은 레인 사이에서만.
3. 워밍업·재시도 오버헤드로 실제는 약간 sublinear(10계정 → 1분 아닌 ~1.2~1.5분).

### ★ IP당 요청예산 = 진짜 제약 (재실측)

한 IP는 워밍 후 ~8~10지역 정상, 그 뒤 스로틀. **지속 수집하면 예산이 더 줄어든다**(실측:
같은 IP 반복 테스트로 실패율 3/12 → 5/12 로 악화). 654지역을 한 IP로는 절대 못 감.
→ **레인당 로테이팅 주거 프록시(IP 수백 풀)** 필수. 몇 요청마다 IP 교체해 각 IP를 예산 안에 유지.
→ 선형단축의 실제 레버 = **계정 수가 아니라 로테이팅 프록시 IP 풀 크기.**
robust 의 `next_proxy` 훅에 로테이팅 풀을 연결하면 빈응답 시 자동 IP 교체.

### ★ 로테이션 전략 실환경 확정 (`proxy_budget.py` + `robust.py`) — 2026-08-26 재실측

프록시 20개로 **실제 당근에 요청을 넣어** 전략을 A/B 했다. 결론이 종전 가정과 반대다.

**① 빈응답은 "IP 워밍"도 "예산 소진"도 아니다 — 시점별 변동이다.**
20회 연속 빈응답이던 IP 3개를 몇 분 뒤 다시 때리자 각각 **1·7·13회만에 성공**했다.
같은 IP·같은 지역이 몇 분 사이 1회 ↔ 25회로 요동한다. 세션(쿠키) 재사용도 성공률을
올려주지 않았다(같은 세션으로 이어 붙여도 25회/12회/1회).
→ 위 "IP당 요청예산 ~8~10지역 후 스로틀" 항목은 **이번 실측으로 재현되지 않았다.**
   IP 는 몇 분 내 회복한다. 다만 "한 IP 안 동시요청 = 전멸"은 그대로 유효.

**② 빈응답이 나면 버티지 말고 즉시 다음 IP 로.** 6개 지역 A/B:

| 전략 | 성공 | 성공까지 요청(median) | 총 소요 |
|---|---|---|---|
| A. 한 IP 고정 재시도 | 4/6 | 23.5회 | 549s |
| **B. 빈응답마다 IP 교체** | **6/6** | **5.5회** | **379s** |

→ 기본값 `empty_rotate_after = 1`. 종전 코드 주석의 "프록시 바꾸면 콜드세션 재워밍 =
   오히려 느림"은 **반증됐다**(그 가정으로 5회 임계를 뒀더니 워밍 완료 직전에 IP 를 갈아
   집 IP 단독(26s)보다 2배 느린 59s 가 나왔다).

**③ 쿨다운은 하드차단·네트워크오류 낸 IP 에만.** 빈응답에 쿨다운을 걸면 멀쩡한 IP 가
풀에서 빠져 풀이 마른다(①). `COOLDOWN_SEC` 300 → **120s**.

**④ `max_retry` 15 → 30.** 교체 전략에서도 성공까지 최대 **29회**가 필요했다.
15 이면 역삼동·삼성동을 통째로 놓친다(= 기존 기본값으로는 누락이 남아 있었음).

**⑤ 백오프는 무의미.** 0.1s vs 0.8s → 요청당 4.99s vs 5.52s, 성공률 동률.
요청 자체가 프록시 경유로 ~5s 라 백오프가 묻힌다. 기본값 0.5s.

`meta.rotations` 로 한 지역에서 IP 를 몇 번 갈았는지 관측 가능(프록시 풀 건강도 지표).

**최종 실환경 검증** — 구 단위 적응형 + 지역 간 휴식, 프록시 20개, 신 기본값:
```
강남구-381   784건  fetch=20 분할=9 포화=True
마포구-408    14건  fetch= 2 분할=0
성동구-405    21건  fetch= 2 분할=0
송파구-424    54건  fetch= 2 분할=0
→ 구별 성공 4/4, 합계 873건, 343s, 쿨다운된 IP 0개
```
강남구 784건은 기존 실측(단일요청 286 잘림 → 적응형 784)과 일치 = 상한 돌파 재확인.

### ★ 레인을 실제 호출부에 연결 — 자동 모니터가 진짜로 빨라짐

`collect_lanes` 는 라이브러리일 뿐이라, 만들어 두기만 하면 사용자에겐 아무 변화가 없다.
실제 실행 경로 세 곳에 붙였다.

**1) manual_gui 자동 모니터 (`daangn/auto_monitor.py`)**
종전 `for reg in regions:` 단일 순차 루프를 `collect_lanes` 로 교체. 지역이 끝나는 즉시
`on_result` 로 그 지역 매물을 받아 **중복제거·알림을 스트리밍 처리**한다(전국이 끝날 때까지
기다리지 않는다). GUI 자동탭에 **레인 스핀박스**를 추가 — `0 = 자동(프록시 수 ÷ 3)`.

레인 수 산정(`_plan_lanes`)은 프록시 수에 종속된다:

| 프록시 | 레인 | 이유 |
|---|---|---|
| 0~1 | 1 | 나눌 IP 가 없다 |
| 6 | 2 | 레인당 3개 확보 |
| 20 | 6 | 20÷3 |
| 20 (지정 4) | 4 | 사용자 지정 우선 |
| 100 (지정 99) | 16 | `MAX_LANES` |
| 2 (지정 2) | **1** | 레인당 3개를 못 채우면 레인을 안 늘린다 |

`MIN_IP_PER_LANE = 3` 인 이유: 레인당 IP 가 1개면 빈응답이 나도 교체할 곳이 없어 그 레인이
통째로 멈춘다(고정 IP 재시도 = 성공 4/6, 중앙값 23.5회).

프록시 목록 변경은 **사이클 경계에서만** 반영한다 — 레인은 시작 시점에 풀을 샤딩해 나눠
갖기 때문에, 도중에 목록이 바뀌면 레인끼리 같은 IP 를 쥐어 "동시요청 전멸" 조건이 된다.

실환경 검증(서울 3개 구, 프록시 20개, 레인 3): **3/3 지역 · 410건 · `found` 시그널 410건 ·
지역별 스트리밍 알림 동작**. `_plan_lanes` 단위 8케이스 + 구조 4케이스 = 12/12 PASS.

**2) auto 독립 러너 (`delivery/auto_runner.py`) — 신규**
`delivery/integrated/auto/` 는 클라 프로젝트에 얹는 드롭인 패키지(`daangn.model` 필요)라
**그 자체로는 실행이 불가능**했다(러너·`asyncio.run` 저장소 전체 0건). `daangn_ext` 만으로
도는 실행 가능한 러너를 새로 만들었다 — `collect_lanes_async` 기반.

```bash
python delivery/auto_runner.py --keyword "샤넬" --proxies proxies.txt \
    --regions OUT.json --lanes 3 --once
python delivery/auto_runner.py --config auto_config.json      # 다중조건·가격범위
```
sqlite 중복제거 + **가격변동 감지**, 신규/변동만 JSONL 적재, 사이클 랜덤 휴식,
Ctrl-C 안전 종료(2회면 즉시), `missed`/`suppressed` 경고 노출.

실환경: 1회차 471건 전량 신규 → **2회차 신규 0 · 변동 1** (실제 가격 165,000→150,000 감지).

**3) 상세 수집 + 크롤 거부 존중 (`daangn_ext/detail.py`) — 신규**
목록 응답에는 판매자 정보가 **아예 없다**(실측 최상위 키 11개, `user` 객체 없음).
따라서 `webCrawlNotAllowed` 판정 자체가 목록만으로는 불가능했다. 상세에서 실측 확인:

```
loaderData["routes/kr.buy-sell.$buy_sell_id"]
    .product.user.webCrawlNotAllowed   ← 판매자 크롤 거부
    .shouldBlock                       ← 당근이 문서 자체를 차단
```

`fetch_detail` 은 거부 매물에 **레코드 대신 None** 을 주고 `meta["refused"]` 에 사유를 담는다.
`meta["ok"]` 로 요청 성공 여부를 따로 표시해 **거부와 실패를 혼동하지 않게** 했다 —
`fetch_details` 집계도 `refused`(존중한 건수)와 `failed`(못 가져온 건수)를 분리해 센다.

목록에 없던 필드가 붙는다: 원본 이미지·조회수·채팅수·관심수·매너온도·리뷰수·
**판매자의 다른 매물 수(전문 리셀러 식별)**·유사매물·정확한 시군구동.

실환경: 단건 1회 성공, 레인4 로 **상세 12건 4.0초**(거부 0·실패 0).
오프라인 11/11 PASS (거부 2종·403 쿨다운·구조변경 조기중단·거부/실패 분리 집계).

### ★ 레인 수 스케일링 — 순차 측정은 시점 변동에 오염된다(주의)

레인 1/2/4/8 을 **순서대로** 돌린 결과(서울 6개 구, 프록시 20개, '구찌 가방'):

| 레인 | 건수 | fetch | 소요 | 속도 |
|---|---|---|---|---|
| 1 | 320 | 18 | 2362.7s | 1.00배 |
| 2 | 320 | 18 | 2352.4s | **1.00배** |
| 4 | 320 | 18 | 1275.0s | 1.85배 |
| 8 | 320 | 18 | 438.0s | **5.39배** |

**이 수치는 그대로 믿으면 안 된다.** 레인2 가 1.00배인데 레인8 이 5.39배인 조합은 모순이다 —
레인8 은 레인당 지역이 1개씩이라 벽시계가 곧 "가장 느린 단일 지역"(438s)인데, 그렇다면
6개 지역 합이 2362s 이므로 지역당 평균 394s 이고 레인2 는 ~1200s 여야 한다.

원인은 앞서 반복 확인된 **시점별 변동**이다. `fetch=18` 이 전 조건 동일하므로 작업량은
같고, 차이는 robust 내부 재시도 횟수뿐인데 그게 시간대에 따라 요동한다(같은 IP·같은 지역이
몇 분 사이 1회 ↔ 25회). 순차 실행이라 레인1·2 는 나쁜 시간대, 레인8 은 좋은 시간대에 걸렸다.

**이 표에서 신뢰할 수 있는 건 딱 하나: 레인 수와 무관하게 320건 동일.**
→ 레인을 늘려도 **매물 손실은 0**. 속도 배수는 교차설계로 다시 재야 한다.

교훈: 이 대상에서 **속도 A/B 는 반드시 조건을 번갈아 실행**해야 한다(앞선 풀 크기 3 vs 20
측정에서도 같은 이유로 결론이 안 났다).

#### 교차설계 재측정 (레인1 ↔ 레인6 을 번갈아 3회씩, 서울 3개 구)

| 회차 | 레인1 | 레인6 |
|---|---|---|
| 1 | 18.4s | 6.5s |
| 2 | 14.5s | 5.7s |
| 3 | 16.4s | 14.1s |
| **중앙값** | **16.4s** | **6.5s** |

→ **2.51배 단축, 건수 34건 전 조건 동일(손실 0).**

**효율 해석 주의**: 지역이 3개뿐이라 레인6 이어도 **실제로 도는 레인은 3개**(3개는 논다).
따라서 이론 상한은 6배가 아니라 **3배**이고, 2.51/3 = **효율 84%**.
레인 수는 지역 수를 넘어서 늘려봐야 소용없다 — `lanes ≤ 지역 수` 를 같이 봐야 한다.

**드리프트 규모의 직접 증거**: 같은 3개 구가 위 6구 측정 때는 지역당 ~400s 였는데
이 측정에서는 **전체가 16s** 였다. 시간대에 따라 100배 가까이 갈린다.
→ 벤치마크는 반드시 교차설계로, 운영 판단은 중앙값으로.

**권장 레인 수** = `min(프록시 ÷ 3, 지역 수, 16)`. 20개 프록시면 6레인이 자동 선택된다.

### ★ 차단 판정 + 진단기 (`block_signals.py` / `health.py`) — 신규

종전 robust 는 **응답 상태코드를 아예 읽지 않았다.** 403(차단)·429(레이트리밋)·5xx·
당근 HTML 구조변경이 전부 "파싱 실패" 하나로 뭉쳐져, 로그를 봐도 **IP 가 막힌 건지
파서가 깨진 건지 구분할 수 없었다.** 이제 6가지로 분류하고 각각 다르게 대응한다:

| 분류 | 신호 | 대응 |
|---|---|---|
| `OK` | 200 + 매물 | — |
| `EMPTY` | 200 + 매물 0건 | 즉시 다음 IP. **쿨다운 안 검**(시점별 변동) |
| `RATELIMIT` | 429 | `Retry-After` 만큼(없으면 600s) 그 IP 쿨다운 |
| `BLOCKED` | 401/403/451 | 그 IP 1800s 쿨다운 + 교체 |
| `CHALLENGE` | 200인데 캡차·봇검증 페이지 | 차단과 동급, 1800s 쿨다운 |
| `SERVER` | 5xx | 당근 장애. IP 잘못 아님 |
| `PARSE` | 200 정상인데 remixContext 없음 | **HTML 구조변경 의심.** IP 갈아도 무의미 |

`PARSE`·`SERVER` 는 IP 를 갈아도 안 풀리므로 연속 `give_up_after`(기본 3)회면
**조기중단**한다 — 종전엔 이런 상황에서 max_retry 만큼 전 프록시를 태웠다.

`meta` 에 `kinds`(분류별 카운트)와 `diagnosis`(한 줄 진단), 조기중단 시 `gave_up` 추가.

**진단기 — "지금 막혔나?" 를 직접 물어본다:**
```bash
python delivery/health_check.py proxies.txt
```
풀의 각 IP 를 1회씩 + 직결 IP 를 찔러 4가지 중 무엇인지 판정한다:
① 일부 IP 만 차단 → 자동 쿨다운, 남은 IP 로 계속
② 풀 전체 차단 → 풀 교체 (직결이 정상이면 프록시 업체 대역 문제)
③ 당근 전면 차단/구조변경/장애 → IP 교체 무의미, 파서 점검 또는 대기
④ 정상

실측 (2026-08-26): **20/20 + 직결 전부 OK, 285건, 1~2s. 차단된 IP 0개.**
지금까지 수백 요청 동안 429·403·캡차 **0건** — 관측된 실패는 전부 `EMPTY`(재시도로 극복).

### ★ 적응형 감속 (`throttle.py`) — 신규

종전 요청간격(`settings.txt` 1줄, `req_min_ms`)은 **고정값**이었다. 429/403 이 쏟아져도
같은 속도로 계속 때리니 차단이 가속됐고, 반대로 아무 문제 없을 때 느린 값을 넣으면
수집만 느려졌다. 운영자가 "적당한 속도"를 미리 맞출 방법은 없다 — 프록시 품질·시간대·
당근 정책마다 다르다. 그래서 **값을 설정 메뉴로 빼지 않고 프로그램이 실측으로 조정**한다.

| 관측 | 조치 |
|---|---|
| `RATELIMIT`/`BLOCKED`/`CHALLENGE` 1회 | 배속 x1.5 (상한 x8) |
| `OK` 20회 연속 | 배속 x0.9 |
| 마지막 차단신호 후 120초 무사고 | 배속 x0.9 (성공 카운트와 무관) |
| `EMPTY`/`SERVER`/`PARSE` | 무관 — 속도 문제가 아니다 |

시간 기반 회복이 따로 있는 이유: 실측상 응답 대부분이 `EMPTY` 라 `OK` 가 드물게 찍힌다.
성공 카운트만으로 회복시키면 한 번 튄 배속이 몇십 분씩 안 내려온다.

배수는 **이미 있던 대기지점에만** 곱한다 — 프록시별 최소간격(`ProxyManager`),
프록시 없는 요청 간격(`ReqLimitter`), 재시도 백오프(`robust`), 지역 간 휴식(`adaptive`,
`auto_monitor`). 새 직렬화 지점을 만들지 않으므로 동시성 구조는 그대로다.
manual(스레드)·auto(이벤트루프)가 전역 상태 1개를 공유한다 — 같은 프록시 풀을 쓰는 이상
어느 경로에서 맞았든 감속은 프로세스 전체에 걸려야 맞다.

고급 조정은 UI 가 아니라 환경변수로만 연다(잘못 만지면 IP 를 태우는 값이라 기본은 숨김):
`DAANGN_THROTTLE=off`, `_MAX=8`, `_UP=1.5`, `_DOWN=0.9`, `_RECOVER=20`, `_CALM=120`.

### ★ 쿨다운 저장소 일원화 (`ProxyManager` ↔ `proxy_budget`)

두 쿨다운 저장소가 분리돼 있었다 — `robust` 가 429 로 600초 쿨다운시킨 IP 를
`ProxyManager` 는 모른 채 곧바로 다시 배정했다. 이제 `ProxyManager.acquire` 가
로컬 쿨다운 + `proxy_budget` 쿨다운을 **둘 다** 보고 IP 를 고른다.
풀 전체가 장기 쿨다운이면 30분을 기다리지 않고 `MAX_STALL_SEC`(20초)만 쉬고
가장 빨리 풀리는 IP 로 진행한다(대안이 없는 상황에선 멈춤보다 진행이 낫다).

역방향은 **일부러 막았다** — 워커 단위 실패(재시도 소진)의 대부분은 빈응답이고,
빈응답에 전역 쿨다운을 걸면 멀쩡한 IP 가 풀에서 빠져 풀이 말라버린다.

### ★ 동시요청 수 자동 클램프 (`CrawlThread`)

`max_workers`(settings.txt 2줄, 기본 16)를 그대로 썼다. 같은 IP 동시요청은 실측상
전멸(8/8 빈응답)인데, 프록시가 5개인데 워커가 16개면 IP 하나에 3중 요청이 꽂힌다.
이제 `min(설정값, 프록시 수)` 로 깎고 그 사실을 메시지로 알린다. 설정값은 상한일 뿐이다.

또한 일반 검색도 `robust` 에 프록시 풀을 넘긴다 — 종전엔 적응형에만 풀을 줘서
일반 검색은 한 IP 로 30회를 두드렸다(A/B: 교체 6/6 성공·중앙값 5.5회 vs 고정 4/6·23.5회).

### ★ GUI 상태 표시 + 진단 버튼 (`manual_gui`)

차단 대응이 전부 자동이라, 사용자에게 필요한 건 **설정이 아니라 지금 상태**다.
상태바 우측에 상시 표시(2초 갱신) + `진단` 버튼:

```
IP 19/20 (쿨다운 1, 540초 후 해제)  ·  간격 1500ms (자동감속 x1.5) · 최근 RATELIMIT 2회   [진단]
```

`진단` 은 `health_check` 를 별도 스레드로 돌려(IP 당 1요청, 8병렬 — 20개 풀 약 2초)
판정·대응·IP별 표를 팝업으로 띄운다. 진단으로 드러난 차단 IP 는 즉시 쿨다운 등록돼
다음 수집이 그 IP 를 다시 태우지 않는다.

### ★ async 판 로테이션 동등화 (`robust_fetch_articles_async`)

기존엔 sync 판에만 `next_proxy`/`proxies` 가 있고 **auto 의 async 판엔 아예 없어서**
하드블록·예외에도 같은 IP 로 15회 재시도했다(자동이 수동보다 약했음).
sync 와 동일하게 `next_proxy`/`proxies`/`should_stop`/예산 쿨다운 지원.
IP 교체 시 `session.cookie_jar.clear()` 로 콜드세션에서 다시 워밍.

### ★ 레인 병렬 수집 (`adaptive.collect_lanes` / `collect_lanes_async`) — 신규

"프록시를 늘리면 빨라지나?" 에 대한 구조적 답. **종전엔 안 빨라졌다** — 자동 모니터는
`QThread` 1개 순차 루프였고(`auto_monitor.py`), `collect_nationwide` 도 지역 단일 for 문이라
프록시를 100개 넣어도 레인은 1개였다. 수동 검색만 `ThreadPoolExecutor` 로 병렬이고,
그 레인 수는 `settings.txt` 2번째 줄(현재 16)이지 프록시 수가 아니다.

`collect_lanes` 는 프록시 IP 를 축으로 실제 레인을 만든다. 설계는 실측 제약 두 개가 강제했다:

  1. **같은 IP 동시요청 = 전멸**(8/8 빈응답) → 한 IP 는 한 순간에 한 요청만
  2. **빈응답 시 IP 교체가 최적**(6/6 vs 4/6) → 레인 안에서는 교체가 가능해야 함

둘을 같이 만족시키려면 **풀을 레인 수만큼 샤딩**해야 한다. 레인들이 풀 하나를 공유하면
robust 의 랜덤 교체가 옆 레인이 쓰는 중인 IP 를 뽑아 (1) 을 위반한다. 샤딩하면 각 레인은
자기 몫 IP 안에서만 교체하므로 두 조건이 동시에 성립한다.
지역은 정적 분할이 아니라 **공유 큐**로 준다 — 지역별 소요가 10배 이상 갈리므로
정적 분할은 느린 레인 하나가 전체를 붙잡는다.

```python
arts, sm = collect_lanes("프라다 가방", regions, proxies=POOL, lanes=4)
# sm["per_lane"] = [{'regions':2,'requests':6,'articles':..,'proxies':5}, ...]
```

`lanes` 미지정이면 프록시 수(최대 `max_lanes`=16). **프록시가 없으면 1레인 = 순차**로
자동 강등되므로 그대로 드롭인 가능. `should_stop` 즉시 반영, 중단 시 `skipped` 로 잔여 지역 수 보고.

**실환경 A/B (2026-08-26, 서울 8개 구, 프록시 20개, "프라다 가방"):**

| 방식 | 건수 | fetch | 소요 |
|---|---|---|---|
| 순차 `collect_nationwide` | 424 | 24 | 1063s |
| **레인4 `collect_lanes`** | **424** | 24 | **425s** |

→ **2.50배 단축, 매물 손실 0** (id 교집합 424 / 양쪽 차집합 0 = 완전 동일 결과).
레인별 부하도 균등(2·2·2·2 지역, IP 5개씩).

**프록시를 늘려서 실제로 빨라지려면** 이 함수를 쓰고 `lanes` 를 같이 올려야 한다.
프록시만 늘리고 레인을 그대로 두면 레인 수는 변하지 않는다.
`collect_lanes_async` 는 auto(aiohttp)용 — **레인마다 ClientSession 을 따로** 만든다
(공유하면 커넥션풀·쿠키가 섞여 레인 격리가 깨진다).

### ★ 지역 사이 랜덤 휴식 (`adaptive.collect_nationwide[_async]`)

기존 지역 순회는 **무휴식 연속 요청** = 한 IP 버스트 → 스로틀 자초.
`rest_range`(기본 `(0.4, 1.2)`초) 로 지역 사이 랜덤 대기. `None` 이면 종전대로 생략.
auto 용 `collect_nationwide_async` 신설 — **순차 + 휴식**이 기본이고, docstring 에
"한 IP 안에서 이 함수를 동시에 여러 개 돌리지 말 것"을 명시(실측 8/8 전멸).
`should_stop` 으로 중도 정지 즉시 반영.

**api.py 래퍼**(patched/·integrated/)에도 `proxies`/`next_proxy`/`should_stop` 통과 추가 —
풀을 넘길 통로가 없으면 로테이션 자체가 무용이었음.

※ 브랜드 9개면 × 9 (또는 프록시 × 9). **증분 모니터는 신규만 → 전국이라도 분 단위.**
※ `auto` 는 이 구조에 맞게 **1프록시:1워커 순차** 로 도는 게 정답(IP 내 동시성 금지).

## 실측 근거 (정지 계정 .ldbk data.vmdk)

토큰 구조 실측 디코드:
```
access : HS256 {iat,exp,code:"z",type:"access"}   exp-iat=1800s = 30분
refresh: HS256 {iat,exp,code:"z",type:"refresh"}  exp-iat=21600s = 6시간
```
→ 클라의 "30분 토큰" = 이 HS256 code 토큰. `token_manager` 가 exp 디코드해 90초 전 자동 refresh.
당근 인증 호스트: `api.kr.karrotmarket.com` (로그인=전화+SMS OTP: `/user/v2/verifications/sms-otp/request`).

## 통합 (5분)

1. `daangn_ext/` 를 manual·auto 각 프로젝트 루트에 복사.
2. 각 `daangn/api.py` 의 `get_products` 에 `access_token`·`rule` 인자 추가 → `integration_examples.py` 그대로.
3. 시작/루프부에 TokenManager + AccountStore + refresh_all 삽입 → 예제 그대로.
4. 브랜드 폴더마다 `accounts.json` (계정+프록시 페어).

## 토큰 위상 — 결론: 당근 수집엔 불필요, 옵션으로 내장 (캡처 불요)

**판정 근거(실측):** 기존 manual/auto 는 `api.py` 에 토큰 0줄로 `www.daangn.com` 익명 GET 하는데도
`OUT.json`·`products.db` 로 실제 수집됨 → **당근 웹 SSR 은 무인증. 토큰 필요 없음.**
`.ldbk` 의 `code:z` 는 HS256 vendor/라이선스 토큰(당근=ES256, 별개) → 당근 요청에 넣어도 효과 0.

따라서:
- **안정성 진짜 엔진 = 프록시 1:1 + 케이던스**(rest_scheduler) — 딜리버리에 포함, 즉시 효과.
- **토큰 레이어 = 옵션.** 클라가 원한 "검색 전 갱신" 구조는 완성해 두되 기본 비활성.
  `auth.TARGET_HOSTS=("karrotmarket.com",)` 라 **www.daangn.com 요청엔 토큰 주입 안 됨(안전 기본값).**
- 훗날 클라가 **당근 인증 API**(`api.kr.karrotmarket.com`, SMS-OTP 로그인)로 전환하거나 vendor
  토큰 서비스를 쓸 때만: 그 순간 1회 캡처 → `token_manager.REFRESH_URL` + `_default_refresh` +
  `auth.py` CONFIG 교체. **지금은 손댈 것 없음.**

→ 외부의존 없음. 딜리버리는 **오늘 그대로 완결.**

## 안정성(밴 회피) — 토큰 밑에 깐 실제 엔진

클라 믿음(토큰=안정)을 수용하되, 실제 안 막히게 하는 3층을 같이 적용:
1. **1계정 : 1프록시** 페어링 (`account_store.add_pair`) — 주거/모바일 프록시 권장
2. **휴식 랜덤 + 요청간격** (`rest_scheduler`)
3. **토큰 사전갱신**으로 세션 일관성 유지

→ 토큰(클라 요구) + 프록시/케이던스(실제 효과) 둘 다 충족.
